## API caveat — `generateObject` deprecated in AI SDK 6.x

AI SDK 6.x에서 `generateObject` / `streamObject` 함수가 **deprecated**. 정식 대체 API:

```typescript
import { generateText, Output } from 'ai';

const result = await generateText({
    model,
    output: Output.object({ schema }),
    prompt,
});
const value = result.output; // typed by schema
```

본 PoC는 deprecation 인지 후 **`generateText` + `Output.object` 정식 path로 마이그레이션 완료**. wire body / structured output mode 동작은 두 API 사이 동일 (둘 다 `responseFormat` 경로로 흘러감). 정식 `createAnthropicProvider` 통합 시 새 path 사용 강제.

추가 발견: `Output.object` 사용 시에도 schema mismatch에서 throw되는 에러는 여전히 **`NoObjectGeneratedError`** (`NoOutputGeneratedError` 아님 — PoC 30 호출 중 한 번도 hit 안 됨). `Output.object`의 내부 path가 legacy `generateObject` 검증 로직을 재사용해서 그런 것으로 보인다. 정식 통합에서는 generic `Error.name` 매칭으로 잡거나 양쪽 모두 isInstance 체크 (§3.1 #5).

## TL;DR

**권고**: **조건부 GO** — `@ai-sdk/anthropic`의 `structuredOutputMode: 'jsonTool'`을 정식 구현에서 **명시적으로 박는다**. `auto`(default)는 Haiku 4.5에서 `outputFormat`과 동등하게 동작하며 wire-level rejection 위험이 있어 회피. **`z.discriminatedUnion`은 양 모드 모두 미흡** → consumer-side flat schema + post-parse refinement 권고.

핵심 발견 4건:
1. **세 모드 결과 정리** — AI SDK Anthropic provider는 `outputFormat` (Anthropic native `output_config.format.json_schema`, beta `structured-outputs-2025-11-13`), `jsonTool` (tool name `"json"` trick), `auto`(default) 3개를 지원. **Haiku 4.5에서 `auto` ≡ `outputFormat`이 10/10 케이스에서 정확히 일치** — capability table(`supportsStructuredOutput: true`)에 따라 `auto`가 항상 `outputFormat` 선택. 즉 명시적 mode 지정이 없으면 `outputFormat` 위험을 그대로 상속.
2. **outputFormat의 wire-level 제약 — 광범위한 bound 거부** — (a) `integer`/`number` 타입에 `minimum`/`maximum` 동반 시 거부, (b) `array` 타입에 `minItems`/`maxItems` 동반 시 거부, (c) `oneOf` 미지원 (discriminated union 차단). zod의 `z.number().int()`/`z.number().min().max()`/`z.array(...).min().max()` 모두 직격. 전부 **`APICallError` (HTTP 400)** 로 fail-fast. **F8 production schema 10곳 이상이 이 패턴으로 즉시 깨진다**.
3. **jsonTool에서도 discriminated union은 약함** — wire body에 `oneOf` 정상 직렬화되지만 모델이 `event` 필드를 **string-encoded JSON으로 wrap** (`{"event":"{\"kind\":\"purchase\"...}"}`) → schema parse 실패. F8의 OpenAI `.nullable()` 권고와 같은 결.
4. **`.nullable()` vs `.optional()` — Claude에서는 동등** — F8 lesson(OpenAI는 strict mode에서 `.nullable()` 강제)이 Anthropic에는 적용 안 됨. C2a(`.nullable()`) / C2b(`.optional()`) 양쪽 모두 3 모드 전체 PASS. 정식 통합 시 consumer가 `.optional()` 그대로 써도 무방.

## 2. 실패 모드 분석

### 2.1 outputFormat — numeric/array bounds 거부 (C1, C4b, C6, C6b)

Anthropic native `output_config.format.json_schema`는 **JSON Schema bound 키워드 일체 미지원**. 검증된 실패 표면 3종:

| 키워드 | 발생 케이스 | 에러 메시지 |
|---|---|---|
| `integer` + `minimum`/`maximum` | C1 (`z.number().int()`), C6 (`z.number().int().min().max()`) | `For 'integer' type, properties maximum, minimum are not supported` |
| `number` + `minimum`/`maximum` | C6b (`z.number().min().max()` non-int) | `For 'number' type, properties maximum, minimum are not supported` |
| `array` + `minItems`/`maxItems` | C4b (`z.array(z.string()).min().max()`) | `For 'array' type, property 'maxItems' is not supported` |

- Wire body 예시 (C4b): `output_config: { format: { type: 'json_schema', schema: { ..., properties: { keywords: { type: 'array', items: { type: 'string' }, minItems: 1, maxItems: 4 } } } } }`
- 원인:
  - `zod-to-json-schema`가 `z.number().int()`에 `minimum:-9007199254740991, maximum:9007199254740991` (`Number.MIN/MAX_SAFE_INTEGER`)를 **자동 attach**
  - `z.number().min(N).max(M)` → JSON Schema `minimum:N, maximum:M`
  - `z.array(...).min(N).max(M)` → JSON Schema `minItems:N, maxItems:M`
  - Anthropic native json_schema는 이들 모든 bound 키워드를 reject
- 빈도: **매우 흔한 패턴**. `z.number().int()` 자동 attach만으로도 거의 모든 numeric 필드 직격. F8 production schema 검증 결과 `topic-issuer.ts`에서 `z.array(...).min(N).max(M)` 16곳 + `topic-recommender.ts`에서 `z.array(...).min(N).max(M)` 2곳 + `z.number().min(0).max(100)` 1곳, 총 19곳이 모두 wire-level fail. **사실상 outputFormat default를 못 쓰게 만드는 결정적 규모**.
- 추가 affected: discriminated union의 variant 안에 bound numeric/array 있으면 oneOf보다 먼저 이 에러 발생 가능. C5 wire body에서도 `code: { type: 'integer', minimum: -..., maximum: ... }` 확인됨.

### 2.2 outputFormat — `oneOf` 미지원 (C5)

- Wire body: `format.schema.properties.event = { oneOf: [...] }`
- 에러: `APICallError: output_config.format.schema: Schema type 'oneOf' is not supported`
- 원인: Anthropic native json_schema가 (현재 beta `structured-outputs-2025-11-13` 시점) `oneOf`/`anyOf`/`allOf` 컴포지션 미지원.
- 영향: zod의 `discriminatedUnion` / `union` 어느 쪽도 사용 불가. F8에서 OpenAI는 `.nullable()`로 우회 가능했지만 Anthropic은 우회 경로 자체가 없음.

### 2.3 jsonTool — 모델 출력이 oneOf variant를 string으로 wrap (C5)

- Wire body: `tools[0].input_schema.properties.event.oneOf = [...]` 정상 직렬화
- 모델 실제 출력: `{"event":"{\"kind\": \"purchase\", \"orderId\": \"ord-42\", \"amount\": 19900}"}` — variant 객체를 **JSON 문자열로 wrap**
- 에러: `NoObjectGeneratedError: response did not match schema` (Zod parse 실패)
- 원인: Claude가 oneOf 처리 시 "variant 객체"를 "object" 대신 "string of JSON" 형태로 출력하는 reliability 결함. 두 단계 모두에서 oneOf가 약점.

## 3. agtlantis 측 인터페이스 영향 평가

T9.1에서 박은 가정 — `provider.streamingExecution` / `BaseFileManager` 시그니처 불변, middleware는 provider 내부 격리 — 은 **유지 가능**. 단, **정식 통합 시 다음 caveat을 박아야 한다**.

### 3.1 정식 `createAnthropicProvider`가 해야 할 일

1. **`structuredOutputMode: 'jsonTool'`을 default로 박는다**. `auto`/`outputFormat`은 numeric/array bound 거부(§2.1)로 흔한 schema들 (`z.number().int()`, `z.number().min().max()`, `z.array(...).min().max()` — F8 production `topic-issuer.ts` 16곳 + `topic-recommender.ts` 3곳 전부)이 wire 단계에서 깨진다. PoC 결과 `auto`는 Haiku 4.5에서 `outputFormat`과 완전히 동일하게 동작하므로 **명시적 mode 지정 없이는 위험 그대로 상속**. consumer가 명시적으로 `outputFormat` 요구할 때만 위임.
   - 구현 위치: `createAnthropicProvider`에서 `providerOptions.anthropic.structuredOutputMode = 'jsonTool'` 자동 inject. 또는 ModelResolver/agent 레벨에서 `anthropic` provider일 때 항상 박힘.
2. **`discriminatedUnion` 사용 schema는 정식 통합에서 unsupported로 marker**. C5는 양 모드 전부 FAIL — `outputFormat`/`auto`는 `oneOf` 미지원으로 API가 직접 거부하고, `jsonTool`은 wire OK인데 모델이 variant를 일관되게 string-encoded JSON으로 wrap (§2.3). **retry로 풀리지 않는 reliability 결함**. 정식 통합 권고:
   - consumer-side에서 `kind` 값으로 자체 분기 후 variant 별로 `generateText` 호출 (variant 마다 일반 `z.object` schema)
   - 또는 단일 `z.object` + 모든 variant 필드를 `.optional()`로 평탄화 + post-parse refinement
   - 정식 `createAnthropicProvider`는 `discriminatedUnion` schema 감지 시 warn-and-fail (또는 docs로 명시) 권고. agent 레벨에서 retry/fallback 로직 박는 것은 위험 — 모델 출력이 일관되게 깨지므로 retry가 비용만 늘림.
3. **`generateText` + `Output.object` path 사용**: `generateObject` deprecated. 정식 통합 코드는 새 path 기준으로 작성. wire body 결과는 동일.
4. **`@ai-sdk/anthropic` 버전 lock**: 본 PoC는 `@ai-sdk/anthropic@3.0.62` (ai-v6 tag) 기준. 향후 SDK가 numeric/array bound 키워드를 strip하거나 oneOf 변환을 추가하면 default 모드 권고 재평가 필요.
5. **에러 catch 분기**: `Output.object` path를 써도 schema mismatch는 여전히 **legacy `NoObjectGeneratedError`** 로 throw (`NoOutputGeneratedError` 아님 — PoC 24 호출 중 한 번도 hit 안 됨, §API caveat 참조). 정식 통합 코드는 다음 형태로 catch:
   ```typescript
   import { NoObjectGeneratedError } from 'ai';

   try {
       /* generateText + Output.object */
   } catch (e) {
       if (NoObjectGeneratedError.isInstance(e)) {
           /* schema mismatch — 흔히 jsonTool에서 모델 출력 불일치 */
       } else if (e instanceof Error && e.constructor.name === 'NoOutputGeneratedError') {
           /* defensive — AI SDK가 향후 error 타입을 통합할 경우 대비 */
       } else if (e instanceof Error && e.constructor.name === 'APICallError') {
           /* wire-level 거부 — outputFormat에서 numeric/array bounds, oneOf (§2.1, §2.2) */
       } else {
           /* unknown */
       }
   }
   ```
   `APICallError`는 `jsonTool` default로 박으면 발생 빈도 낮지만, consumer가 `outputFormat`을 명시적으로 override 또는 fallback path 사용 시 대비 분기 권고.

**본 권고의 정식 Feature 청사진 위치**: T9.1 §3.4의 1단/2단/3단 분리 표 기준으로 **본 권고 1~5번 전부 2단(Provider 통합)에 흡수**. 1단(`AnthropicFileManager`)/3단(Prompt caching)에는 영향 없음. T9.5 GO/NO-GO 결정문에서 통합 시 본 §3.1을 2단 구현 체크리스트로 인용.

### 3.2 BaseFileManager / Provider 인터페이스 영향

- **없음**. structured output은 `generateText`/`streamText` 호출 표면의 `output` + `providerOptions` 만으로 처리. 인터페이스 contract 변경 0.
- T9.1 결정의 "BaseFileManager 인터페이스 yes" 박힘 유지.
- T9.4의 "조합형" 검증 시 본 T9.3의 `structuredOutputMode: 'jsonTool'` 권고를 전제로 webSearch + thinking + structured output 3중 조합을 검증.

### 3.3 F8 비교

| 항목 | OpenAI (F8) | Anthropic (T9.3) |
|---|---|---|
| Strict structured output mode | `gpt-5.4` Responses API native | `output_config.format.json_schema` beta (제약 多) |
| Tool-use fallback | `responseFormat.tool` | `tool name "json"` |
| `.nullable()` 필요? | YES (OpenAI strict는 모든 optional → nullable 요구) | NO (jsonTool은 optional 그대로 OK, outputFormat도 nullable 처리 OK) |
| Discriminated union | OpenAI strict mode에서 일부 OK | **양 모드 모두 깨짐** (Anthropic의 약점) |
| `integer + min/max` | OpenAI 통과 | **outputFormat에서 깨짐** |
| `number + min/max` (non-int) | OpenAI 통과 | **outputFormat에서 깨짐** (C6b) |
| `array + minItems/maxItems` | OpenAI 통과 | **outputFormat에서 깨짐** (C4b) |

→ **T9.5 인계**: 본 비교 표가 Google grounding(F8 archive)까지 합치면 **3-provider × N-schema 매트릭스** 형태가 된다. T9.5 GO/NO-GO 결정문 또는 정식 Feature 1단(인프라)에 **`provider-specific Zod schema guidance` 영역 신설** 권고. consumer가 schema 짤 때 어느 패턴이 어느 provider에서 깨지는지 단일 reference. 본 §3.3 표는 그 표의 시작점.
