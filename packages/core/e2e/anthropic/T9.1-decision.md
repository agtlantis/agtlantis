# F9-T9.1 결정 — FileManager 추상화 정체성

> Spike 산출물. Throwaway. 정식 구현 X.
> 작성: worker-T9.1 (Slate). Date: 2026-05-12.

---

## TL;DR

**권고**: **조건부 GO — Option B' (Files API 메인 + inline 보조, AI SDK fetch middleware 우회 레이어)**.

핵심 근거: PoC Case 5에서 `file_id` + `cache_control: ephemeral` 조합이 **2차 호출 cache_read 46,207 tokens 풀 적중** 확인. 멀티턴 분석 use case의 cost 구조가 성립한다. AI SDK가 입력 `file_id`를 1급 지원하지 않는 한계는 `createAnthropic({ fetch })` middleware로 흡수 가능 — `BaseFileManager` 인터페이스 변경 없이 처리 가능.

**미커버 영역**: 생기부 50MB+ PDF는 inline path(32MB) 차단, Files API path(500MB 한도)로 회피 가능. 단, **600 pages / 200k 컨텍스트 모델은 100 pages 한도** 제약은 별도 영역 (분할 전처리 필요할 수 있음).

## 1. 사실 정리 (T9.1.1 + T9.1.2 통합)

### Anthropic file 입력 3 mechanism

| Mechanism | content block | Size limit | AI SDK 지원 | 비고 |
|---|---|---|---|---|
| **inline base64** | `image.source.type:'base64'` / `document.source.type:'base64'` | request 전체 **32MB** | ✓ 자동 (FilePart→image/document로 변환) | data: Buffer/string |
| **URL reference** | `image.source.type:'url'` / `document.source.type:'url'` | request 32MB (URL 자체) | ✓ 자동 (URL 객체 인식) | URL이 base-file-manager의 inline 분기와 동일 패턴 |
| **Files API beta (file_id)** | `image.source.type:'file'` / `document.source.type:'file'` | upload **500MB/file**, **500GB/org** | ✗ **입력 미지원** | header `anthropic-beta: files-api-2025-04-14` 필수. **TTL 없음** (persist until delete). beta status |

### PoC 검증된 사실 (Haiku 4.5, 실제 호출)

- **AI SDK inline path 무결**: 188KB png → AI SDK가 자동으로 base64 변환하여 호출. 응답 정상. 1,567 tokens.
- **AI SDK file_id 입력 차단**: `FilePart.data: 'file_xxx'` 문자열은 base64로 강제 해석 → API 거부 (`invalid base64 data`). type system + runtime 모두 막혀있음.
- **Raw REST file_id 정상**: 같은 파일을 `source: { type: 'file', file_id }` 형태로 직접 호출하면 정상 동작.
- **여러 file_id 동시 첨부**: 단일 메시지에 image 2개 file_id 정상 ([Case 2]). iPhone 4-5장 시나리오 mechanism 동작 (실제 상한은 docs 미명시 — request size 32MB 한계로 자연스럽게 제약).
- **PDF + image 혼합**: 같은 메시지 정상 ([Case 4], 47,769 tokens, 605KB PDF + 138KB image).
- **file_id + cache_control 호환** ([Case 5]):
  - 1차 호출: `cache_creation_input_tokens = 46,207`, `cache_read = 0`
  - 2차 호출: `cache_creation = 0`, `cache_read = 46,207` (full hit, ephemeral_5m)
  - → **멀티턴 분석 cost 절약 가능성 확정**. Haiku 4.5 base read rate × 0.1 효과.

### AI SDK x ai 6.x 호환

- `@ai-sdk/anthropic@3.0.62` (npm dist-tag `ai-v6`) → ai^6.0.0, LanguageModelV3.
- 최신 `@ai-sdk/anthropic@3.0.76`은 ai 5.x용 (`latest` tag). **6.x는 ai-v6 tag 또는 4.0.0-beta.x 사용 필요**.
- `createAnthropic({ headers, fetch })` 둘 다 1급 옵션. middleware 우회 길이 열려 있음.
- 알려진 버그 [`vercel/ai#10018`]: AI SDK가 자동 inject하는 `anthropic-beta`가 user-supplied 헤더를 덮어쓰는 케이스 존재. PR #10158 진행 중. **Files API 헤더(`files-api-2025-04-14`)는 자동 inject 대상 아님** → 영향 낮음 (PoC에서도 정상 전달 확인).

## 2. 3안 Trade-off

기존 plan에서 정의된 A/B/C를 PoC 결과로 갱신. Option B는 AI SDK 한계 발견으로 **B'**로 확장.

### Option A — inline-only

`AnthropicFileManager.uploadToProvider`가 모든 source를 inline part로 반환, `id: null`. URL은 base-file-manager의 기존 분기로 자연 흡수.

| 평가 축 | 결과 |
|---|---|
| 인터페이스 변경 | ✗ 없음 |
| OpenAI/Google 영향 | ✗ 없음 |
| iPhone 사진 4-5장 (~15MB) | △ 32MB request 한계 안. 단, system+history+text 합치면 빠르게 차오름 |
| **생기부 PDF 수십 MB** | ✗ **inline 32MB 한계에 직격** |
| 멀티턴 cache 적중 | △ inline base64 content에 cache_control 가능하지만, file 콘텐츠 자체가 매 요청 body에 실리므로 wire 비용은 줄지 않음 |
| beta 의존성 | ✗ 없음 (안정) |
| 구현 난이도 | 낮음 |
| **use case 적합성** | **부적합** — 생기부 PDF가 main use case라서 |

### Option B' — Files API 메인 + inline 보조 (★ 권고)

`AnthropicFileManager`가 두 path를 분기:
- **path/data/base64 large** → Files API beta 업로드 → `UploadedFile.id = "file_xxx"`, `part`는 raw block을 표현하는 **provider-specific marker**
- **path/data/base64 small** (threshold 5MB 등) → inline `{type:'file', data: Buffer, mediaType}` (AI SDK 1급)
- **url** → 기존 base-file-manager url 분기 그대로 (inline part, `id: null`)

AI SDK가 `file_id` 입력을 1급 지원 안 하므로 둘 중 하나:
1. **fetch middleware**: `createAnthropic({ fetch: rewriteMiddleware })` — outbound JSON body를 가로채서 inline part의 marker를 raw `{source:{type:'file',file_id}}` 블록으로 교체.
2. **provider-side adapter**: agtlantis `AnthropicProvider`가 사용자 메시지를 AI SDK에 넘기기 전에 자체 변환 (provider 내부 책임).

| 평가 축 | 결과 |
|---|---|
| 인터페이스 변경 | ✗ **없음** — `BaseFileManager.uploadToProvider` 시그니처 유지. `UploadedFile.id` 의미가 자연 확장 (null = inline, string = file_id) — F7 OpenAI와 동일 |
| OpenAI/Google 영향 | ✗ 없음 |
| iPhone 사진 4-5장 (~15MB) | ✓ Files API path. cache_control과 결합하면 멀티턴 cost 절약 |
| **생기부 PDF 수십 MB** | ✓ Files API 500MB까지. **PoC Case 3에서 605KB PDF → 46k tokens 검증 완료** |
| 멀티턴 cache 적중 | ✓ **PoC Case 5에서 cache_read 46,207 풀 적중 확인** |
| beta 의존성 | △ `files-api-2025-04-14` beta header 필수. GA 일정 미공개 — Anthropic docs는 stable 승격 시 마이그레이션 안내 약속 |
| 구현 난이도 | 중상 — middleware/adapter 1개 + Files API REST client 1개 (OpenAI FileManager 패턴 재사용 가능) |
| AI SDK 버그 risk | △ #10018 영향 가능성 낮음 (자동 inject 대상 아님) — 정식 구현 전 fix 버전 채택 권고 |
| **use case 적합성** | **적합** — 100% 커버 가능 (단, 100 pages 제한 PDF는 별도 처리) |

### Option C — `FileManager` 인터페이스 손질

`UploadedFile` 타입에 `provider-specific raw` 필드 추가, 또는 `FileManager.upload` 시그니처 변경 등.

| 평가 축 | 결과 |
|---|---|
| 인터페이스 변경 | ✗ 강제 변경 (OpenAI/Google 코드도 손봐야 할 수 있음) |
| OpenAI/Google 영향 | ✗ **확산 영향** |
| use case가 강제하는가? | ✗ **아니오** — Option B'로 인터페이스 불변 처리 가능 |

**Reject 이유**: use case가 인터페이스 변경을 강제하지 않는다. Option B'가 같은 결과를 인터페이스 불변으로 달성. F8 lesson "조합형 폭발 + 인터페이스 변경은 cost 큼"과 부합.

### 3.3 AI SDK 우회 레이어 — 검증된 코드 + 의사코드

#### 3.3.1 검증된 코드 — PoC에서 실제 동작한 raw REST 형태

다음 두 패턴은 PoC `file-input.poc.test.ts` 안에서 **실제 ANTHROPIC API 호출로 검증 완료**. middleware/adapter가 wire-time에 만들어내야 하는 최종 wire 형태가 바로 이것.

**(a) Files API beta `file_id`로 image/document 참조** — PoC Case 1·2·3·4 모두 정상 응답 (Haiku 4.5):

```typescript
// 인용: file-input.poc.test.ts — Case 1 raw REST(image, line 197-204),
//      Case 2 멀티 image(line 222-230), Case 3 PDF(line 244-251),
//      Case 4 PDF+image mixed(line 268-276)
const rawResp = await messagesRaw({
    model: MODEL_HAIKU,
    beta: [FILES_BETA],
    content: [
        { type: 'text', text: 'Describe this image. One sentence.' },
        { type: 'image', source: { type: 'file', file_id: fileId } },
        // 또는: { type: 'document', source: { type: 'file', file_id: fileId } }
    ],
});
```

**(b) `messagesRaw` helper — wire body 자체 형태** (인용: file-input.poc.test.ts:395-416):

```typescript
async function messagesRaw(params: MessagesRawParams): Promise<AnthropicMessagesResponse> {
    const resp = await fetch('https://api.anthropic.com/v1/messages', {
        method: 'POST',
        headers: {
            'x-api-key': ANTHROPIC_API_KEY!,

            max_tokens: 256,

    });
    // ...

```

**(c) `createAnthropic({ fetch })`가 user fetch를 그대로 호출한다는 사실** — PoC Case 6의 fetchSpy로 outbound body 캡처 성공 (file-input.poc.test.ts:50-82 `makeFetchSpy`). middleware 패턴이 실제로 wire를 가로채는 길이 열려 있음을 증명.

→ middleware/adapter의 책임은 단순: AI SDK가 직렬화한 inline base64 형태(`{ type: 'image', source: { type: 'base64', media_type, data } }`)를 위 (a) 형태로 교체. 양 끝점 모두 PoC 코드 안에 실제 동작 형태로 존재.

#### 3.3.2 의사코드 — middleware 구조

`createAnthropic({ fetch })`의 `fetch` 시그니처는 표준 `fetch`와 호환. middleware는 다음 형태:

```typescript
// AnthropicFileManager가 large file을 업로드한 결과의 `part`에 marker 심음.
// 예: { type: 'file', data: 'agtlantis-file-id:file_abc123', mediaType: 'image/png' }
// 또는 providerMetadata로 흘림 (AI SDK 6.x providerMetadata 표면 활용).

const FILE_ID_PREFIX = 'agtlantis-file-id:';

function rewriteFileIdMiddleware(fetchImpl: typeof fetch): typeof fetch {
    return async (input, init) => {
        if (!init?.body || typeof init.body !== 'string') return fetchImpl(input, init);

        const url = typeof input === 'string' ? input : input instanceof URL ? input.toString() : input.url;
        if (!url.endsWith('/messages')) return fetchImpl(input, init);

        const body = JSON.parse(init.body) as { messages: Array<{ content: unknown[] }> };
        for (const msg of body.messages ?? []) {
            if (!Array.isArray(msg.content)) continue;
            msg.content = msg.content.map((block) => transformBlock(block));
        }
        return fetchImpl(input, { ...init, body: JSON.stringify(body) });
    };
}

function transformBlock(block: unknown): unknown {
    if (!isPlainObject(block)) return block;
    // AI SDK가 직렬화한 inline image/document block 중 data가 marker로 시작하면 raw file_id 블록으로 교체
    const source = (block as { source?: { data?: string; type?: string } }).source;
    if (source?.type === 'base64' && typeof source.data === 'string' && source.data.startsWith(FILE_ID_PREFIX)) {
        const fileId = source.data.slice(FILE_ID_PREFIX.length);
        return { ...block, source: { type: 'file', file_id: fileId } };
    }
    return block;
}
```

**검증된 부분**:
- `createAnthropic({ fetch })` 옵션 존재 (`@ai-sdk/anthropic@3.0.62` `d.ts` line 1056).
- raw REST `{ source: { type: 'file', file_id } }` 호출 정상 동작 (PoC Case 1·2·3·4·5 모두).
- AI SDK가 user fetch를 그대로 호출 — PoC Case 1에서 fetchSpy로 outbound body 캡처 성공.

**미검증 부분 (정식 Feature 1단에서 e2e 추가)**:
- AI SDK가 ImagePart/FilePart를 직렬화할 때 marker가 어느 필드(`source.data` vs 다른 표면)에 실리는지 정확 위치 확인.
- providerMetadata 경유 vs in-band marker 경유 중 더 안정적인 표면 결정.

대안 — provider-side adapter: agtlantis `AnthropicProvider` 내부에서 user의 messages를 AI SDK에 넘기기 전에 자체 변환 (provider responsibility). middleware는 wire-time, adapter는 build-time. **양쪽 다 인터페이스 불변. 정식 Feature에서 채택안 결정.**

### 3.4 정식 구현 Feature 청사진 — 1단/2단/3단 분리

| 단 | 범위 | 산출물 | 독립 머지 가능? |
|---|---|---|---|
| **1단 — Uploader** | `AnthropicFileManager extends BaseFileManager` + Files API beta REST client + size-threshold 분기 (inline vs file_id) | `packages/core/src/provider/anthropic/file-manager.ts`, `e2e/anthropic/file-manager.e2e.test.ts` | ✓ — `createAnthropicProvider` 없이도 standalone 사용 가능 |
| **2단 — Provider 통합** | `createAnthropicProvider` + middleware (또는 adapter) + index.ts export + peerDep `@ai-sdk/anthropic` (optional) | `packages/core/src/provider/anthropic/factory.ts`, `index.ts` 갱신, `package.json` peerDep | ✓ — 1단 완료 전제. 2단 단독으로 기존 OpenAI/Google 코드 영향 없음 |
| **3단 — Prompt caching 통합** | `cache_control` 옵션 정식 노출 + `FileCache`↔Files API 매핑 + usage extractor의 `cache_creation/read_input_tokens` 분리 | `packages/core/src/session/usage-extractors.ts` 갱신, `packages/core/src/pricing/defaults.ts` Claude rate 보강 | ✓ — F9 design의 P1 항목. 2단 후 즉시 시작 가능 |

각 단은 독립 머지 가능 + 각각 e2e 추가 가능 → F8 lesson "조합형 폭발 직전 단독 검증"과 부합.

**Spike 단계 dependency 정책 (peerDep vs devDep)** — Spike 동안 `@ai-sdk/anthropic`은 `devDependencies`에만 둔다. peerDep은 consumer에게 "이 패키지는 Anthropic provider를 지원한다"는 contract 신호이며, 정식 `createAnthropicProvider` / `AnthropicFileManager` 없는 상태에서 노출은 misleading. integrity 우선 → devDep만, 정식 Feature(2단)가 peerDep + provider 코드 + README 묶음으로 일관 처리한다.

### 3.5 Fallback path (inline-only) 영구 유지 권고

정식 구현 시에도 **inline-only path를 영구 살리는 것을 권고**:

| 시나리오 | inline path 필요성 |
|---|---|
| Files API beta deprecate / GA 좌초 | **유일한 fallback** |
| ANTHROPIC_API_KEY가 Files API 비활성화된 워크스페이스 | inline으로 동작 보장 |
| small file (<1MB)에서 Files API roundtrip 오버헤드 회피 | latency 최적화 |
| Zero Data Retention 워크스페이스 | Files API beta는 **"not eligible for ZDR"** 명시 (Anthropic Files API docs 직접 확인). inline path는 일반 Messages API 보유정책 적용 — 거버넌스 요구 시 inline path 우선 검토 권장. **PDF inline path 자체의 ZDR 적용 여부는 별도 검증 필요** (Anthropic PDF support 페이지는 "feature is eligible for ZDR" 명시했으나 inline base64 path와 file_id path 간 차이는 docs로만 단정 못 함) |

→ 구현 형태: `AnthropicFileManager` 생성 시 `{ strategy: 'auto' | 'inline-only' | 'files-api-only' }` 옵션. default `auto` (size threshold). 운영에서 강제 inline 가능.

### 3.6 T9.4가 가정할 인터페이스 형태

T9.4(webSearch + thinking + structured output 조합형)는 **인터페이스 변경 없는 Option B' 위에서** 검증한다. 즉:
- `provider.streamingExecution(fn)` 시그니처 불변
- 사용자 코드에서 `fileManager.upload(...)` 결과를 그대로 `messages.content`에 흘리는 패턴 유지
- 차이는 provider 내부 (middleware) 에 격리

## 4. `BaseFileManager` 인터페이스 호환성 — yes/no 박기

**결론: YES — 인터페이스 변경 없이 Anthropic Claude 흡수 가능.**

### 4.1 시그니처 변경 없음

- `BaseFileManager.uploadToProvider(source, index): Promise<UploadedFile>` 추상 메서드 그대로 사용. OpenAI/Google 구현 영향 0.
- `UploadedFile = { id: string | null, part: FilePart | ImagePart }` 타입 그대로 사용.
- `FileManager`, `FileCache`, `FileSource` discriminated union 모두 손대지 않음.

### 4.2 `UploadedFile.id` 의미 충돌 정리

| Provider | `id: null` 의미 | `id: string` 의미 |
|---|---|---|
| 기존 OpenAI (F7) | URL source (외부 URL, OpenAI 업로드 안 함) | OpenAI Files API `file-xxx` |
| 기존 Google | URL source 동일 | Google Files API id |
| **Anthropic (Option B')** | URL source **또는** inline base64 (size < threshold) | Anthropic Files API `file_xxx` |

**의미 충돌 해석**: F7 시점 `id: null`은 "외부 URL, 우리가 관리 안 함" 의미였음. Anthropic에서 `id: null`은 두 케이스 — (a) URL source (b) inline base64. **base-file-manager.ts:27-37의 url 분기는 이미 inline part를 반환하고 `id: null`을 박는다** — 즉 "id: null = 사용자가 별도 delete 호출 안 해도 됨"이 더 정확한 invariant. Anthropic의 inline 케이스도 이 invariant를 만족 (provider 측 storage 없음). **의미 충돌 아님, 의미 일반화**.

### 4.3 `part` 필드 의미 충돌 정리

| Provider | `id: string`일 때 `part` 내용 |
|---|---|
| OpenAI | `{ type: 'file', data: fileId, mediaType, filename }` — AI SDK가 `file_id` 입력 1급 지원 |
| Google | 동일 패턴 |
| **Anthropic** | `{ type: 'file' \| 'image', data: marker, mediaType }` — middleware가 wire-time에 raw block으로 교체 |

→ **part 필드의 wire 의미는 같음** (LLM 호출에 그대로 사용). 차이는 wire-time 변환 책임자(OpenAI/Google = AI SDK / Anthropic = 우리 middleware). 인터페이스 contract 변하지 않음.

### 4.4 향후 인터페이스 진화 시 호환성

만약 미래에 AI SDK가 입력 file_id를 1급 지원하게 되면:
- middleware 제거 가능.
- `AnthropicFileManager`의 `part` 필드를 `{ type: 'file', data: file_id }` 형태로 자연 전환.
- 외부 contract (`UploadedFile.part`) 변경 없음 → consumer 코드 무영향.
