## 4. Root cause — 왜 거부되는가

### 4.1. Anthropic API 정책

`Thinking may not be enabled when tool_choice forces tool use.` — Anthropic의 정식 정책(API 측 enforcement, 400 with `invalid_request_error`, `isRetryable: false`).

### 4.2. AI SDK가 만드는 wire 모양

`@ai-sdk/anthropic@3.0.62`에서 `structuredOutputMode: 'jsonTool'` 활성 시:

| Step | 위치 | 동작 |
|---|---|---|
| 1 | `dist/index.js:2940-2947` | `jsonResponseTool` 만들어짐 (name `"json"`, function tool with input schema) |
| 2 | `dist/index.js:3198-3204` | jsonTool 활성 분기 → `tools: [...userTools, jsonResponseTool]`, **`toolChoice: { type: 'required' }`** 강제, `disableParallelToolUse: true` 강제 |
| 3 | `dist/index.js:1576-1585` | `prepareTools()`가 `'required'` → wire **`tool_choice: { type: 'any', disable_parallel_tool_use: true }`** 로 변환 |
| 4 | Anthropic API | thinking이 켜져 있고 `tool_choice.type ∈ {any, tool}` → 400 거부 |

즉 SDK가 의도적으로 만드는 `tool_choice` 강제 패턴이 Anthropic의 thinking 호환 정책과 정면 충돌한다.

## 5. Scenario C 부산물 — 정상 path의 사실들

C(thinking + webSearch, no structured output)는 정상 동작. 정식 통합 시 활용할 사실들:

### 5.1. Interleaving pattern (T9.2 Open question 답)

```
R[ → R] → tc(web_search) → tc(?) → tc(web_search) → tr(web_search) → T[ → T] → ... (T blocks × 12)
```

- **reasoning 블록은 toolCall 시작 전에 완전히 닫힌다** (`reasoning-end` → `tool-input-start`)
- reasoning chunk와 tool chunk는 **interleave하지 않는다** — 순차 단일 step
- T9.2의 단일 reasoning 블록 결과와 정합

### 5.2. webSearch tool wire payload

```jsonc
{ "type": "web_search_20250305", "name": "web_search", "max_uses": 2 }
```

- Provider tool ID 매핑: `anthropic.web_search_20250305` → server name `web_search` (compiled SDK `dist/index.js:2965`)
- 옵션: `maxUses`, `allowedDomains`, `blockedDomains`, `userLocation` (모두 optional, `dist/index.js:1107-1118`)

### 5.3. webSearch usage tracking

```jsonc
"usage": {
  "raw": {
    "input_tokens": 18020,
    "output_tokens": 653,
    "server_tool_use": {
      "web_search_requests": 1,
      "web_fetch_requests": 0
    }
  }
}
```

`usage.raw.server_tool_use.web_search_requests`가 실제 사용 횟수. 정식 Anthropic provider의 usage extractor에서 cost 계산 시 활용 권장 (pricing table에 web_search rate 추가 필요 — P1).

### 5.4. Citation 형태 — `source` chunk × 16

C 시나리오에서 `source` type chunk가 16건 등장. webSearch citation 데이터 (URL/title/pageAge/encryptedContent — compiled SDK `dist/index.js:1124-1130` schema). 정식 통합 시 citation 정규화 layer 필요 — Google grounding / OpenAI webSearch citation과 매핑 검토는 T9.5 청사진에 인계.

## 6. 정식 Anthropic provider Feature 시 회피 패턴

`jsonTool + thinking` 4중은 wire-level rejection 확정. F8 production scenario(topic-issuer의 `streamText({ output: Output.object, ..., searchTools })`)를 Claude로 그대로 들고 갈 수 없다. 그러나 **Option C(outputFormat) 검증 결과로 회피 path가 1-phase 단일 호출까지 단순화 가능**해졌다.

### Option A: thinking 비활성화 + structured output + webSearch (3중)

**가장 단순.** thinking 없이는 jsonTool과 양립 가능 (Scenario B/D root cause는 `thinking + tool_choice='any'`라 thinking 끄면 해결). 단점: **reasoning quality 손실.** topic-issuer는 ModelResolver `reasoning: 'high'` 명시 path라 product 결정 필요.

### Option B: 2-phase pipeline (reasoning phase → structured output phase)

```
Phase 1: thinking + webSearch (no structured output) → raw markdown / freeform text 산출
Phase 2: no thinking + structured output (jsonTool) → Phase 1 산출물을 schema 정리
```

- 호출 2번 (cost ↑), 그러나 **F8 production schema(.min/.max bound 19곳) 그대로 사용 가능**
- Phase 1은 본 PoC Scenario C에서 정상 동작 확인됨
- F8 OpenAI에서 hang 안 났던 verification phase와 구조 동일 (F8 `topic-issuer.ts:426-461` `runVerification` 참고)
- **Option C가 schema 마이그레이션 부담을 못 받을 때의 fallback**

### Option C: outputFormat mode 단일 호출 ★ (PoC로 입증)

```
1-phase: thinking + webSearch + structuredOutputMode='outputFormat' → parsedOutput 정상 산출
```

- **Scenario F PoC 입증** (`38s, okStreamed=true, parsedOutputPresent=true`).
- Wire 모양: `output_config.format.type='json_schema'`, **json 함수 tool 미주입**, `tool_choice` 강제 없음
   → compiled SDK `dist/index.js:2941`의 `useStructuredOutput=true` 분기가 jsonResponseTool 생성 자체를 skip → thinking + tool_choice='any' 충돌 영역 자체를 우회
- **★ 제약 (T9.3 정합)**: outputFormat은 **schema bound 키워드 거부** (numeric `min/max`, array `minItems/maxItems`, `oneOf`, discriminatedUnion 등 — T9.3 §3.1 #1). F8 production schema 19곳을 **이 영역에 맞게 마이그레이션** 필요 (bound 제거 또는 `.describe()`로 옮기기)
- **Reasoning 패턴 (★ 신상)**: webSearch 사용 시 reasoning 블록이 **tool 호출 전후로 2번** emit (`R[→R] → tc → tr → R[→R] → T[`) — Scenario C(tool 후 reasoning 안 열림)와 다름. consumer가 multi-block reasoning을 받을 수 있다는 점은 stream 처리 로직 설계 시 반영

### Option D: Provider-specific behavior — agent-level 분기

ModelResolver / agent factory 레벨에서 `provider === 'anthropic'` 분기:
- topic-issuer가 Anthropic provider 받으면 Option B(2-phase) 또는 Option C(outputFormat + schema 마이그레이션) 적용
- topic-issuer가 OpenAI/Google provider 받으면 기존 1-phase 유지

F8 lesson("searchTools는 ModelResolver가 아닌 agent 레벨")과 정합. ModelResolver는 모델 선택만, agent가 provider-aware 분기.

### 권고 (rook, Option C 검증 후 갱신)

**1순위: Option C (outputFormat) + Option D (agent-level 분기)** — schema 마이그레이션 부담 감수 가능한 영역.

- 이유:
  - 단일 호출로 thinking + webSearch + structured output 가능 (Scenario F PoC 입증)
  - 호출 cost 절약 (Option B 대비 ~½)
  - F8 verification phase와 별도 — production 1-phase 그대로 유지 가능
- 마이그레이션 비용: F8 schema 19곳에서 `.min/.max/.int()` 일부 제거 (T9.3 finding §3.3 매핑 그대로 사용)

**2순위: Option B (2-phase) + Option D** — schema 마이그레이션 불가/지연 시 fallback.

- F8 schema 그대로 사용. 호출 2번이지만 thinking 품질 보존
- Phase 2가 F8 topic-issuer verification path (`runVerification`) 재활용 가능 → 추가 인프라 0

**선택 기준**: 정식 Anthropic provider Feature가 양쪽 path를 모두 지원하고, agent별로 (schema 종류 + product 요구) consumer가 옵션 선택. ModelResolver는 모델만, agent factory가 path 결정.

**Option A는 reasoning 손실이 큼** — 기존 ModelResolver `reasoning: 'high'`가 박힌 agent들에 product 영향 평가 없이 적용 불가.

## 7. F8 vs F9 비교 — 폭발 모드

| 축 | F8 (OpenAI gpt-5.4) | F9 (Anthropic Sonnet 4.6) |
|---|---|---|
| 4중 조합 실행 결과 | 3분+ hang → TTL eviction loop | **400 invalid_request_error, ~300ms 즉시 fail** |
| 에러 시그널 | silent (timeout만) | **명시적 message로 root cause 박힘** |
| Retry 권장 | n/a (hang은 retry 의미 없음) | `isRetryable: false` (Anthropic header) → retry 무의미 |
| 디버깅 비용 | 매우 높음 (격리 테스트 통과/실제 앱 실패) | **낮음** (첫 호출에서 명시 fail) |
| 회피 비용 | rework 크기 큼 (provider 교체 + 모든 reasoning 우회) | **2-phase로 한정 가능** (verification phase 재활용) |
| 단독 축 안정성 | thinking only OK, webSearch + structured OK | 동일 |

**결론**: Anthropic의 실패 모드는 **F8보다 안전한 종류의 실패**다 — 폭발이 silent이 아니라 explicit이고, retry 가드도 자체적으로 들어 있다. 그러나 4중 조합 자체는 OpenAI와 마찬가지로 불가능. 우회 패턴은 **OpenAI보다 명확하게 설계 가능**.

## 8. T9.5 인계 (GO/NO-GO 결정 + 정식 Feature 청사진)

### 8.1. T9.4 결론 요약 (T9.5가 결정문에 박을 6줄)

1. **Anthropic Claude(Sonnet 4.6)는 F8 OpenAI의 "3분 hang" 패턴을 재현하지 않는다.**
2. 그러나 `thinking + tool_choice='any'/'tool'/'required'` 조합은 API 측에서 **명시적 400 거부** (`Thinking may not be enabled when tool_choice forces tool use.`).
3. AI SDK `structuredOutputMode: 'jsonTool'`이 wire-level `tool_choice='any'`을 강제하므로 (compiled SDK `dist/index.js:3198-3204`, `1576-1585`), **jsonTool + thinking 조합은 항상 거부됨**.
4. F8 production schema (topic-issuer `IssuanceResultSchema`) 들고 4중 → 같은 root cause. **schema 복잡도와 webSearch는 변수가 아니다.**
5. **★ Option C (`outputFormat`) PoC 입증** — Scenario F (thinking + webSearch + outputFormat) **단일 호출 PASS, parsedOutput 정상 산출** (38s, F8 대비 silent hang/explicit reject 모두 회피). 단, schema 마이그레이션(bound 키워드/oneOf 제거 — T9.3 §3.1 #1) 필요.
6. **GO** — 회피 path 2개 모두 검증됨: **Option C(outputFormat 단일 호출, schema 마이그레이션 필요)** 1순위, **Option B(2-phase, schema 그대로)** fallback. Option D(agent-level 분기)와 조합.

## 11. AI SDK 6.x ToolSet typing quirk — provider tools와 ToolSet incompatibility

**Review-work 중 발견** (worker-T9.4, 2026-05-12). T9.5 정식 Feature 청사진 1단 인프라에 반드시 인계할 영역.

### 11.1. Diagnostic (재현)

```
e2e/anthropic/web-search-combo.poc.test.ts:270:39
Argument of type '{ ..., tools: { web_search: Tool<...> } }' is not assignable to parameter of type 'CallSettings & ...'
Types of property 'tools' are incompatible.
Property 'web_search' is incompatible with index signature.
Property '[schemaSymbol]' is missing in type 'Schema<{ query: string; }>' but required in type 'Schema<never>'.

L315 (별개): Property 'experimental_output' does not exist on type 'StreamTextResult<...>'.
L328: 동일한 ToolSet 부적합 (no-structured-output path)
```

### 11.2. Reveal 명령

| 명령 | scope | 결과 |
|---|---|---|
| `pnpm tsc --noEmit -p tsconfig.json` | `include: ["src/**/*"]` → e2e/ 제외 | ✅ 0 errors (false negative) |
| `npx tsc --noEmit ... e2e/anthropic/web-search-combo.poc.test.ts` | 직접 파일 타겟 | ❌ 3 errors reveal |
| (lead 측 project-level tsc, e2e 포함) | full scope | ❌ 3 errors reveal |

→ **self-check가 e2e/ 범위를 빠뜨려 false negative.** T9.1 §3.8에서 이미 식별된 "F7+F9 공통 e2e 인프라 결함 (tsconfig include `src/**/*` 한정)" — T9.4에서도 동일하게 영향. T9.5 1단 인프라 cleanup에 e2e tsconfig include 확장 권장 (T9.1 인계와 정합).

### 11.3. Root cause

`ai@6.0.39 dist/index.d.ts:408`:

```typescript
type ToolSet = Record<string, (Tool<never, never> | Tool<any, any> | Tool<any, never> | Tool<never, any>)
  & Pick<Tool<any, any>, 'execute' | 'onInputAvailable' | 'onInputStart' | 'onInputDelta' | 'needsApproval'>>;
```

`Pick<..., 'execute' | ...>` 가 `execute`를 **required**로 추출한다.
그런데 provider tools (`@ai-sdk/anthropic`의 `webSearch_20250305()` 등)는 **server-side execution** — `execute` 함수를 들고 있지 않다. 결과 type:
- `Tool<{ query: string }, { type: 'web_search_result'; ... }[]>` (no `execute`)
- `ToolSet` index signature와 incompatible (execute 누락 + input schema generic `{query:string}` vs `never`)

→ **AI SDK 6.x type 결함**. 런타임은 정상 (PoC 6/6 PASS, Scenario C webSearch 정상 실행). type 시스템이 provider tools 변종 처리 미흡.

### 11.4. L315 별건: `stream.experimental_output` 접근 시 TS2339 (generic 추론 path 영역)

**정정 (2026-05-12, verifier #thorn 캐치)**: 본 finding 초안은 "streamText 결과에 experimental_output 자체가 없음"으로 적었으나 사실 부정확. `ai@6.0.39 dist/index.d.ts`를 직접 확인하면:

- `StreamTextResult<TOOLS, OUTPUT>` interface (`:1985`)에 `experimental_output` (`:2788`, `@deprecated`) + `output` (`:2793`) **둘 다 readonly property로 존재**
- `GenerateTextResult<TOOLS, OUTPUT>` interface (`:2677`)도 동일 (`:1127`+`:2156`)
- `:1127`/`:2446`은 별개 — `generateText`/`streamText` **call options**의 deprecated `experimental_output` input parameter

원본 TS2339 메시지 (RTK tee log `1778584225_tsc.log`, verbatim):

```
L315: Property 'experimental_output' does not exist on type 'StreamTextResult<ToolSet, Output<unknown, unknown, never>>'.
```

**진짜 root cause 영역**: result interface에 property는 존재한다. 문제는 generic `OUTPUT`이 `Output<unknown, unknown, never>`로 추론된 상태에서 발생. property type은 `InferCompleteOutput<OUTPUT>`인데 `OUTPUT = Output<unknown, unknown, never>`일 때 conditional type evaluation이 깨져 TypeScript가 `experimental_output` 접근을 거부.

**같은 시그니처인 `output` (`:2793`)이 fix 후 PASS하는 이유** (단정 어려운 TS 내부 영역, 관찰 사실만 기록): 두 property가 동일하게 `InferCompleteOutput<OUTPUT>` 타입을 갖는데도 `experimental_output`만 거부되고 `output`은 통과. 가능한 영역:
- deprecated JSDoc tag가 property resolution path에 영향
- 한쪽 property 접근 시 generic 재추론이 다르게 evaluate
- `Output.object({ schema })` return type 자체가 schema generic을 좁히지 못해 `never`가 들어가는 경로 차이

원인 단정 없이 **관찰된 fact**만 박는다:
1. `experimental_output`는 `@deprecated` property로 result interface 안에 존재
2. `Output.object` 결합 시 `experimental_output` 접근만 TS2339, `output` 접근은 OK
3. fix는 stable property `output` 사용으로 단순화 (deprecation 정합 + 관찰된 issue 회피)

정식 Anthropic provider Feature가 `Output.object`를 사용할 때 동일 generic 추론 path를 탈 수 있으므로 **`stream.output`/`result.output`을 표준으로 박는 권고**가 §11.6 1단 인프라 가이드 안에 정합 (consumer가 deprecated property를 일부러 잡지 않도록).

### 11.5. Fix 적용 (review-work, 본 spike 안)

PoC code 변경 (review-work fix scope):

```typescript
// L48-49: import ToolSet type
import { NoOutputGeneratedError, Output, streamText, type ToolSet } from 'ai';

// L237-247: provider tool 직접 ToolSet 자리에 넣을 때 명시 cast
const tools = cfg.withWebSearch
    ? ({
          web_search: anthropicProviderTools.tools.webSearch_20250305({
              maxUses: cfg.webSearchMaxUses ?? 2,
          }),
      } as unknown as ToolSet)
    : undefined;

// L315: experimental_output → output (stable property)
parsedOutput = await stream.output;
```

검증:
- `tsc` (e2e 파일 직접 타겟): **3 errors → 0 errors**
- `vitest`: **6/6 PASS, 20.90s** (재실행, 결과 회귀 0건. 같은 400 거부 메시지/wall-clock/매트릭스 정합)
